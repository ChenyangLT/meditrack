## 一、先说结论：为什么"系统通知调用总是有问题、无法准时通知"

旧的提醒实现把**闹钟当成了事实来源**：为每个剂量挂一个精确闹钟，再加一个"次日午夜"的维护闹钟，然后就信任它们。

这套设计有三个致命缺陷，任意一个都会让提醒**永久静默消失**，而且现场不留任何痕迹：

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | **单点依赖**。自愈链只有"午夜那一个维护闹钟"这一根线。 | 该闹钟一旦被 OEM 后台清理、被强制停止、或在 Doze 中被丢弃，**未来所有提醒全部失效**，直到用户恰好打开应用。午夜恰恰是 Doze 最深、厂商清理任务最活跃的时刻。 |
| 2 | **没有周期性核对**。一天 24 小时里只有到点那一次机会。 | 任意一个 `PendingIntent` 被系统丢掉，这个剂量就再也不会响。国内 ROM 上这是常态，不是异常。 |
| 3 | **提醒次数上限由"时间"推算，而不是由"提醒次数"**。旧代码：`次数 = (now - 上次提醒) / 重复间隔`，再截断到上限。 | 剂量被提醒过一次后，只要过了 20 分钟，推算出的"次数"就已经等于上限，**后续所有重复提醒被静默吞掉**。配额不是被提醒用掉的，是被时钟用掉的。 |

另外还有三个独立的小 bug，各自都能让一类提醒永远发不出来：

- **未服药提醒永远发不出来**：漏服扫描和"已通知"标记写在同一条 SQL UPDATE 里。扫描在启动、每次心跳、每次开机都会跑，因此总是抢先占掉"已通知"标记 —— 真正的通知代码检查该标记后就直接返回了。
- **"稍后提醒"会让剂量掉出排程窗口**：排程查询只看 `plannedTimeMillis`。用户一按"稍后"，计划时间变成过去，该剂量立刻掉出窗口，只剩 snooze 那一刻挂上的**孤零零一个**闹钟。它再被丢一次，提醒就彻底没了。
- **"稍后提醒" = 提醒凭空消失**：只是取消通知 + 显示 4 秒 toast。用户屏幕上再也没有任何东西说明"这次药还欠着、几点会再来"。

## 二、新架构：数据库是唯一事实来源，闹钟只是提示

一句话原则：

> **每一次触发都从数据库从零重算并重排全部提醒，且该过程幂等。**

这正是 Chrono 的做法 —— `updateAlarms()` 会取消全部闹钟、遍历持久化的闹钟列表、逐个重排；它在**每次触发、开机、后台 fetch、前台服务 tick** 时都调用同一个函数。因此 Chrono 可以丢掉任意一个闹钟而无感恢复，因为**没有任何一个闹钟是"某件事到期了"的唯一记录**。

### 四条互相独立的触发路径，全部汇入同一个 `ReminderEngine.reconcile()`

| 路径 | 时机 | 作用 |
| --- | --- | --- |
| 精确闹钟 | 每个剂量的到点时刻 / 提前预告时刻 | 主路径 |
| **自检心跳** | 默认**每 15 分钟**（可调 10–180） | 丢失任一闹钟，最多延误一个周期 |
| WorkManager 周期任务 | 默认每 15 分钟 | **机制不同**（JobScheduler），故障模式不同，互为备份 |
| 系统事件 | 开机 / 时区变更 / 时间变更 / 应用更新 / 启动 / 回到前台 | 立即重建全部排程 |

因为 `reconcile()` 幂等，四条路径同时到达也不会重复提醒：先到的做事，后到的发现无事可做。

**这就是"提高检测频率"的答案**：从"一天一次"变成"最多 15 分钟一次"，并且是不依赖单一路径的冗余。

## 三、纠错能力（每一条都对应一种"静默消失"）

1. **永不提前** —— 触发时刻比计划早出容差窗口（默认 5 分钟 + 提前预告窗口）时，判定为时钟跳变 / 过期 `PendingIntent`，**重新排定而不是弹出提醒**。
   该规则**只对"声称自己是这个剂量的闹钟"的触发生效**（`DOSE_ALARM` / `PRE_ALARM`）。心跳、开机、启动本来就会扫到几小时后的剂量，把它们当异常只会淹没真正的信号。
2. **永不迟到太久** —— 超过迟到阈值（默认 3 小时）的提醒**不再弹横幅**，降级为静默的「如果已经吃过，点一下补记」。避免重启后为早上 8 点的药在凌晨 3 点把人吵醒。
3. **次数上限是存储的计数器** —— 新增 `dose_logs.escalationCount`，`markNotified` 每次 +1。旧实现"时间耗尽配额"的 bug 从根上消失。
4. **未服药提醒可达** —— `deriveMissed()`（只推导状态）与 `markMissedNotified()`（认领通知）拆成两条语句。今天的漏服仍能发出一次通知；**历史日期**的扫描仍会一并占掉标记（旧日期的漏服不该再打扰用户）。
5. **"稍后"重新打开配额** —— `snooze` 清空 `notifiedTimeMillis` / `escalationCount` / `preRemindedAtMillis`。"稍后"的语义是"到新时间再好好提醒我一次"。
6. **已稍后的剂量不会掉出窗口** —— 排程查询改为 `MAX(COALESCE(snoozedUntilMillis, plannedTimeMillis), plannedTimeMillis)`（SQL 版的"有效到点时刻"）。这是 `tools/verify_dao_sql.py` 里被单独写成回归断言的那一条。
7. **精确取消** —— 已排程剂量 id 记录在 `ReminderAlarmRegistry`，因此"取消全部"是精确操作，不会留下会响的孤儿闹钟。
8. **心跳永不被例行重算取消** —— 只取消"每剂量"闹钟。若在重算开始时把心跳一起取消、结束时再挂回，中间就存在"进程被杀 ⇒ 一个闹钟都不剩"的窗口。
9. **决策审计** —— `reminder_events` 记录每次决策：触发器、投递/跳过、跳过原因、**系统实际延迟毫秒数**。设置页可直接查看，回答"为什么 8 点没提醒我"。
10. **自检与修复** —— 设置页核对权限、心跳是否停滞、实测最大延迟，给出可执行建议，并提供「立即自检并修复」与「发送测试通知」（真实通道、真实铃声设置）。

## 四、人性化提醒（不精确到秒）

| 原来 | 现在 |
| --- | --- |
| 到点弹一次「计划 08:00」 | 到点前先来一次「还有 15 分钟：阿司匹林」（同时是同一剂量的**第二条独立投递路径**） |
| 标题写 `08:00` | 标题写「早上 8 点左右」；精确分钟仍在展开详情里，临床精度不丢 |
| 每种药各弹各的 | 几分钟内到期的药合并成一条摘要，子通知保留各自按钮 |
| 只认"到点那一秒" | 整条管线没有任何一处对两个时刻做相等比较；晚到几秒/几分钟都只是"准时" |
| 按「稍后」→ 通知消失 | 留下安静的「已推迟：阿司匹林 / 将在 08:35 再提醒你」+「现在服用」按钮，到点被真正的提醒替换 |
| 免打扰时段内静默发一条没人看得到的通知 | **顺延到时段结束再发** |
| 晚到装作无事 | 超过 2 分钟才送达时，详情里说明"本次提醒比计划时间晚了 N 分钟" |

取整**向下**到 5 分钟是有意的：永远不会报出比实际计划更晚的时间，也不会跨到相邻时段（08:58 说"早上 8 点 55 分左右"，而不是"上午 9 点"）。

## 六、怎么用

1. 安装 `MediTrack-release-1.1.0-*.apk`（与旧版同一签名，可直接覆盖安装，**数据保留**：v2→v3 为纯增量迁移）。
2. 打开 **设置 → 提醒可靠性**：
   - 看自检结论与建议；
   - 点「发送测试通知」确认通道正常；
   - 点「立即自检并修复」重建全部闹钟；
   - 若实测延迟较大，开启「闹钟级提醒」（`setAlarmClock`，不受 Doze 影响，代价是状态栏出现闹钟图标）。
3. **设置 → 提醒方式**：调整提前预告与提前量、合并时段、稍后状态保留、补记提示、免打扰顺延。
4. **设置 → 最近的提醒决策**：查看每次提醒做了什么决定、以及为什么没有提醒。

> 建议第一次安装后做两件事：把「药准时」加入电池优化白名单、在系统设置里允许自启动 —— 这两项是唯一应用无法自己申请的权限，自检会明确提示。

# 附录 A · v1.2.0 桌面小组件尺寸重做

## A.1 原来的问题

小组件只有一个条目，默认 **2×2**，用三个硬编码高度阈值（130dp / 200dp）查表决定显示几行：

```kotlin
val maxRows = when {
    size.height < 130.dp -> 2
    size.height < 200.dp -> 3
    else -> 6
}
```

问题有两个，互相叠加：

1. **阈值与真实行高无关**。一行是「药名 + 时间·剂量」两行文字加内边距，实际约 38dp；但阈值假设一行只占 30dp 左右。于是刚好越过阈值的尺寸（例如 130dp 的 2×2）会要求 3 行，而 3 行加标题需要约 130dp 以上的空间——超出的部分被 Launcher 直接裁掉。
2. **`SizeMode` 用的是默认的 `Single`**。Glance 在 `Single` 模式下只在创建时组合一次，用户拖动缩放后**不会重新组合**，缩放过的格子会一直沿用出生时的布局。

再加上 2×2（约 110dp 宽）本来就装不下"状态点 + 图标 + 药名 + 时间 + 剂量 + 状态"，于是"2×2 显示有问题"。

## A.2 现在的做法

### 四种独立尺寸，固定 4 列宽

| 条目 | 默认 | 可缩放到 | 实际显示 |
| --- | --- | --- | --- |
| 药准时 · 单行 | 4×1 | 4×1 起任意拉大 | 无标题，1 项（最紧急的） |
| 药准时 · 双行 | 4×2 | 同上 | 标题 + 2 项 |
| 药准时 · 三行 | 4×3 | 同上 | 标题 + 3 项 |
| 药准时 · 四行 | 4×4 | 同上 | 标题 + 最多 4 项 |

四种尺寸在 Launcher 的小组件列表里**分别出现**，各有自己的预览图（由 `tools/make_widget_previews.py` 按同一套几何参数生成，不会与实际渲染脱节）。

### 关键修复

1. **行数由真实高度算出，不再查表**
   `WidgetSizing.layoutFor(width, height, …, fontScale)` 是纯函数：先算出"标题 + 一行"是否放得下，再算放得下几行，并用**松弛量**判断溢出提示那行是否有空余位置可以占用（占不到就不画，绝不为此挤掉一行药）。
   不变式：**占用的高度永远不超过格子的高度**——这条由 `WidgetSizingTest` 在 40–400dp、6 档字号、4 档条目上限的组合上逐个断言。

2. **宁可不要标题，不能不要药**
   4×1 放不下"标题 + 一行药"，于是丢掉标题只显示那一项药。少一个标题，远好过把药名裁掉一半。

3. **`SizeMode.Exact`**
   这是"缩放后依然正确"的前提。没有它，四种尺寸的意义只剩下"首次摆放时的默认大小"。

4. **字号跟随系统**
   行高按 `Configuration.fontScale` 缩放（文字缩放、内边距不缩放，分开建模）。本应用自带"适老模式"会调大系统字号——不跟随的话，模型恰好会对最需要看清它的用户裁切内容。实测 1.5× 字号下 4×2 会正确地从 2 行降为 1 行，而不是硬塞 2 行后被裁。

5. **缩放下限锁死在 4×1**
   四个条目的 `minResizeWidth = 250dp`、`minResizeHeight = 40dp`，因此**任何条目都不可能被拖成装不下内容的形状**，从结构上消除了这一类问题。

6. **极短格子退化为单行密集模式**
   如果连两行文字都放不下（例如 1.5× 字号下的 4×1），就不再画两行然后裁掉第二行，而是改成"状态点 + 药名 + 时间 + 状态"的单行形式。

7. **一次刷新覆盖全部四种**
   `GlanceAppWidget.updateAll()` 只会更新**它自己那个子类**对应的格子（Glance 按 `GlanceAppWidget` 的 class 反查 receiver）。四种尺寸就必须一起刷，否则改了数据只有一个尺寸会更新。所有刷新统一走 `WidgetRefresh`。

8. **顺手修掉一个从未生效的设置**
   「显示条目数量」这个偏好项一直只被存储和备份，**没有任何代码读取它**。现在它作为行数上限真正生效：能放几行由格子高度决定，显示几行取两者较小值，设置页也补上了说明文字。

## A.4 怎么用

1. 安装 `MediTrack-release-1.2.0-*.apk`（同一签名，可直接覆盖 1.1.0 / 1.0.0，数据保留）。
2. 长按桌面 → 小组件 → 药准时：会看到四个条目，按想要的行数选一个。
3. 放上去之后可以自由拖动边缘缩放；宽度不会小于 4 格，高度不会小于 1 格。

# 附录 B · v1.3.0 解决「只有打开应用才提醒」

## B.1 先说结论

这个现象有一个非常明确的技术含义：

> **应用被系统从后台清理掉了，连同它排好的所有闹钟一起。**

不是"闹钟晚了"，也不是"某个闹钟丢了"——那样的话你至少会看到迟到的通知。**一个通知都没有，只在打开应用后一次性全部出现**，说明在两次打开应用之间，应用及其全部待触发闹钟都被取消了。

这也解释了为什么 v1.1.0 的四条独立路径（精确闹钟 / 15 分钟心跳 / WorkManager / 系统事件）都没能救回来：**它们都是"计划好的唤醒"，而清后台取消的正是所有计划好的唤醒。** 加再多的闹钟也没用，它们在同一次清理里一起消失。

真正能对抗这件事的只有一个机制：**前台服务**（一条常驻通知，让系统不把应用当成可回收的后台进程）。Chrono 也正是为此保留了前台服务。

## B.2 本次改动

| 改动 | 说明 |
| --- | --- |
| **后台守护服务**（新增，默认开启） | 常驻前台服务，保持进程存活。这是唯一能对抗"清后台"的机制。通知本身静音、无震动、不显示角标，只在通知栏最底部可见 |
| **闹钟级提醒**（改为默认开启） | `setAlarmClock` 是 Android 唯一不受 Doze 影响的闹钟类型，而且系统把它当作"用户可见的闹钟"来对待，厂商清理时更不容易动它。代价是状态栏有一个闹钟图标——对用药提醒来说，这个图标反而正好是"闹钟已排定"的可见凭据 |
| **被系统丢弃的闹钟（新证据）** | 每次排定闹钟时，同时记下"为哪个剂量、排在了什么时刻"。之后如果发现"排过、时间已过、却从未提醒"，就明确记为一次 `ALARM_LOST`。**这直接把责任分清了**：是应用没排（我们的 bug），还是系统没触发（需要守护服务 + 自启动） |
| **自启动直达入口** | 设置页新增一键跳转到厂商的「自启动 / 后台运行」页面（小米、华为、OPPO、vivo、三星、魅族等已知组件名逐個尝试，都没有时回落到应用详情页） |
| **自检面板新增两项** | 「后台守护服务」是否在运行、「被系统丢弃的闹钟」累计次数。丢掉过闹钟时，建议里会直接给出结论 |

## B.3 装好之后请做这三件事

1. 打开应用一次 —— 建立自检心跳与守护服务。
2. **设置 → 提醒可靠性**：
   - 确认「后台守护服务」开关是**开**的（默认开）；
   - 点「打开系统「自启动 / 后台运行」设置」，把药准时加进白名单；
   - 点「把药准时加入电池优化白名单」（若显示未加入）。
3. 回到设置页顶部看自检结果：
   - **「被系统丢弃的闹钟」显示 0** → 一切正常；
   - **显示大于 0** → 说明系统确实在清理后台，请务必完成上面第 2 步的全部三项。

## B.4 如果仍然不行

打开 **设置 → 最近的提醒决策**，那里会明确记录问题出在哪一侧：

- `ALARM_LOST` / 「已排定的闹钟未被系统触发」→ 系统在清理后台，属于厂商 ROM 行为；
- 有排定记录但没有触发记录 → 同样是系统层面没有交付；
- 连排定记录都没有 → 是应用侧的问题，请附上这段日志提 issue。

有了这个日志，就不需要再猜了。

## B.5 诚实说明

本次改动**没有在真机上验证过**（开发环境没有连接任何设备）：

- 前台服务能否在各厂商 ROM 上稳定常驻、常驻通知是否被允许显示；
- 厂商的自启动页面组件名是否与各系统版本一致；
- `ALARM_LOST` 检测是否会被正常触发。

已完成的验证是：编译通过、**189 个单元测试全部通过**（新增 `LostAlarmDetectionTest` 13 例，覆盖丢失判定规则与"排定记忆"的编解码）、release APK 中确认服务与权限已正确声明（`foregroundServiceType=specialUse`、`stopWithTask=false`、`PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 均就位）。

如果在你的设备上仍然不正常，请把「设置 → 提醒可靠性」的截图和「最近的提醒决策」一并提 issue——有了 `ALARM_LOST` 这类证据，就能直接定位是系统还是应用。
