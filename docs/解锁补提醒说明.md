# 药准时 v1.5.0 · 解锁补提醒（修复「熄屏期间的提醒被抵掉」）

> 用户报告：**手机熄屏期间到点的吃药提醒会「被抵掉」**——锁屏上不亮、不震动、不响；有时甚至连通知都没有，解锁或打开应用后也不会补出来。与此同时，设置页的「发送测试通知」一切正常。
>
> 这一版做了两件事：把提醒在**解锁手机（或回到应用）的那一刻**补上，并加入「提醒多少次 / 间隔多久」的设置；同时修掉管线里两个会让提醒静默消失的真实缺陷。

---

## 一、先说结论：为什么会被「抵掉」

### 1. 提醒到点时，屏幕是黑的

系统闹钟（`setAlarmClock`）确实会响。但普通通知在**锁屏、装在口袋里**的时候，用户看不到；而提醒的应用层逻辑无法知道「这条通知有没有被看见」。

### 2. 等应用再次运行时，剂量已经过期，于是只留下一条**静默**通知

管线的时间窗是这样的（默认值）：

| 时刻 | 判定 | 表现 |
| --- | --- | --- |
| 计划时间 08:00 | `Remind` | 高优先级通道：横幅 + 上锁屏 + 震动 |
| 08:00 – 08:30 | 仍在宽限期内 | 仍然是 `Remind`（可听见） |
| 08:30 之后 | `Missed`（未服药） | **静默**：`CHANNEL_MISSED`，`enableVibration(false)` |
| 超过 3 小时 | `CatchUp`（补记） | **更静默**：`CHANNEL_REMINDER_SILENT`，IMPORTANCE_LOW |

也就是说：**「没人看见的那次提醒」只有 30 分钟的窗口能以可听见的方式补发。** 超过 30 分钟，管线就开始「安静地记账」，而不是「再提醒一次」。用户看到的现象就是「被抵掉」。

### 3. 一个真实的查询缺陷：已判定为「未服药」的剂量会被整条管线无视

`getOverdueOpen`（查「过期但还没处理」）与 `getArmableBetween`（查「该排闹钟」）都写成：

```sql
WHERE status IN ('UPCOMING', 'DUE', 'PARTIAL')
```

而 `MISSED` **不在里面**。更糟的是：`sweepMissed()`（把过期未记录的剂量标记为未服药）**在同一次 reconcile 里、收集候选之前**就运行了。于是流程是：

1. 08:31 任意一条路径唤醒应用；
2. `sweepMissed` 把 08:00 那一行改成 `MISSED`；
3. 紧接着的候选收集里，这一行**既不在过期查询里（MISSED 被排除），也不在未来的排程窗口里（时间已过）**；
4. 唯一还能捞到它的是第四条来源：`epochDay = 今天 AND MISSED AND missedNotified = 0`。

第 4 条覆盖不了两种情况：**跨过午夜的剂量**（epochDay 变成昨天，会被 `repairHistory` 顺手把 `missedNotified` 一起占掉），以及**任何一次已经写过未服药标记的剂量**。这两种情况下，剂量从此不在任何候选集合里——**连一条静默通知都不会有**，这正是用户说的「完全没有通知，解锁/打开应用后也不会出现」。

**修复**：`getOverdueOpen` 不再排除 `MISSED`（这条现在有回归断言守着）。

## 二、新逻辑：解锁补提醒

### 2.1 触发

| 触发 | 说明 |
| --- | --- |
| **解锁手机**（`ACTION_USER_PRESENT`） | 锁屏被解除的那一刻 |
| **亮屏且未锁屏**（`ACTION_SCREEN_ON` + `KeyguardManager.isKeyguardLocked == false`） | 已经解锁的手机被唤醒（从口袋里拿出来） |
| **回到应用**（`MainActivity.onStart`） | 打开或切回药准时 |

这三条广播**不能静态注册**（平台禁止），只能运行时注册。因此由 `MediTrackApp` 在进程启动时注册（不再像旧功能那样「只有开关打开时才注册」），并由默认开启的**后台守护前台服务**保证进程存活。这是无法绕过的边界：进程被杀、且系统不重建它时，解锁广播收不到——此时仍有兜底：**下次打开应用会立刻补提醒**。

### 2.2 哪些药会被补提醒

对每一个「已经设置过的时间点」，同时满足以下全部条件才会提醒：

1. **未点击「稍后」**（或稍后的时间已经到了）；
2. **状态是「未吃药」**：数量为 0 且已过计划时间、只吃了一部分、或已被判定为「未服药」——三种都算；
3. **已经吃过 / 已跳过 的不提醒**；
4. 迟到的时长仍在设置里的「**多久之后算太晚了**」之内（默认 3 小时，可在「提醒方式」里改）；超过这个范围只安静地记为未服药；
5. 该剂量当天的**补提醒次数还没用完**，且距上次补提醒已超过**最小间隔**。

> 时间是绝对时刻，不是「几点几分」：稍后提醒会把「有效到点时刻」一起推后，因此「稍后到点」之后该剂量重新变为可提醒。

### 2.3 提醒形式

| 项 | 行为 |
| --- | --- |
| 一次解锁有 1 项未吃 | 一条普通提醒：「还没吃：阿司匹林」+ 已服 / 稍后 / 跳过 |
| 一次解锁有 ≥2 项未吃 | 合并成一条「你还有 N 项没吃」，**只震动一次**；每项仍作为静默的子通知保留自己的按钮 |
| 通道 | 与普通提醒完全一致：横幅 + 上锁屏 + 震动（是否响铃沿用「提醒铃声」开关） |
| 锁屏可见性 | `VISIBILITY_PUBLIC`：锁屏上直接显示药名与按钮 |
| 免打扰时段内 | **只留一条静默通知，不响不震动**，且**不消耗**可听见的次数（次数留给用户愿意被打扰的时段） |
| 全屏提醒（可选，默认关） | 像系统闹钟一样点亮屏幕并盖在锁屏之上；Android 14+ 需要在系统设置里手动允许，未允许时自动退化为横幅 |

### 2.4 「提醒多少次」怎么算

- 设置项：**每个药提醒多少次**（1–10，默认 3）、**两次补提醒之间至少间隔**（不限制 / 5 / 10 / 15 / 30 分钟，默认 5）。
- **从第一次解锁提醒开始算**：计数与「普通重复提醒」的计数器是**两个独立的计数器**，互不占用。
- **每解锁一次最多用掉一次**（不会因为反复解锁而在几分钟内用完）。
- **每个药、每天各算各的**：剂量行本身就是「某天的某一次」，所以次数天然按天重置。
- 吃药 / 跳过 / 重置记录 / 点「稍后」都会重新打开这份配额。

### 2.5 与旧「手机未使用时暂缓提醒」的关系

**旧的闲置暂缓功能已退役。** 它的做法是「没人看的时候先把提醒压住，等用户回来再发」——而压住的这段时间正好会让剂量越过宽限期，于是补发出来的是**静默的未服药通知**，这正是「被抵掉」的成因之一。现在不再压住任何提醒：计划内的提醒照常在到点时响，解锁补提醒只是在它之外**再加一次机会**。

字段与备份格式仍保留（老备份可以正常导入，只是不再影响行为）。

| 列 | 说明 |

| `dose_logs.unlockReminderCount` | 该剂量已发出的解锁补提醒次数（默认 0） |
| `dose_logs.unlockReminderAtMillis` | 上次补提醒的时刻（用于最小间隔） |

### 字体自适应（同一版）

系统字号与应用内字号会**相乘**（系统 1.3× + 特大 1.3× = 1.69×），设置页那排「5 分钟 / 10 分钟 / …」的选项最先被挤爆。两部分修复：

1. **总字号封顶 1.6×**（`FontScaling.effectiveAppScale`）：只削减应用自己那部分，系统字号仍由平台应用；极端系统字号下保留 0.8× 的下限以免把用户要的大字变小。
2. **布局自适应**：所有选项按钮改为可换行的 `FlowRow`；去掉会裁掉内容的 `maxLines=1 + Ellipsis`；固定宽度的文本列改为 `weight`；日历单元格由固定高度改为最小高度。

## 五、真机上额外发现并修复的三个缺陷

这些都是**只有装到真机上看数据才会暴露**的问题，与解锁补提醒同源（都属于"提醒/状态悄悄消失"），因此一并修掉。

### 5.1 无限重算风暴（最严重）

**现象（从设备上拉出的审计表）**：86 秒内写入 491 条 `GUARD_SERVICE` 重算记录，中位间隔 **22 毫秒**，最多一秒 24 次。整个审计表（保留 500 条）只覆盖了 90 秒，"最近的提醒决策"面板因此**永远只能看到最近一分半钟**。

**根因**：`reconcile()` 结尾会调用 `ensureRunning()` 请求守护服务，而 `startForegroundService` 对一个**已在运行**的服务只是再投递一次 `onStartCommand` —— 于是：

```
reconcile() → ensureRunning() → onStartCommand() → reconcile() → ensureRunning() → …
```

**后果**：每秒 ~25 次取消并重排全部闹钟、持续占用 CPU、常驻通知被反复重发、审计轨迹被冲掉、`ALARM_LOST` 永远无法成立（期望值每秒被重写）。对一台会被"清理后台"的国产 ROM 来说，这正好是最容易被冻结的行为。

**修复**：只有"守护不见了"或"守护已超过 3 分钟未报到"时才请求它（`GuardLiveness.needsRestart`），并让服务**在做任何事之前**先写下存活时间戳 —— 它触发的那一次重算就能看到这个新鲜时间戳，循环在一次额外重算后自然结束。

**实测**：空闲 60 秒内重算 **0 次**（修复前约 1500 次/分钟）。

### 5.2 已到点的剂量仍显示「未到时间」

**现象**：真机截图显示 22:49 的剂量（提醒**已经发过**）在 22:54 的今日卡片上写着「未到时间」，而同一张卡片上另一行写着「已过 5 分钟」。

**根因**：剂量行是在**时间到之前**创建的（提醒管线会预物化未来几天），写入时状态就是 `UPCOMING`，而没有任何代码会在时间到点时回头改写它 —— 唯一会改的是宽限期之后的漏服扫描。于是整个「到点 ~ 宽限期」窗口内，卡片都在说"还没到时间"，`DoseView.isOverdue`（它要求 `DUE`）也永远无法生效，「未服药」红标形同虚设。小组件因为早就改用时钟判断，反而是对的 —— 只有应用内卡片错了。

**修复**：`DayPlanner.displayStatus` 把 `UPCOMING` 视为"尚未决定"，按当前时钟重新推导；其余状态都是用户行为的结果，时钟无权推翻。

### 5.3 状态胶囊忽略了 isOverdue

卡片的重音色已经按 `isOverdue` 变红，但胶囊调用的是单参数重载（`isOverdue = status == MISSED`），所以迟到的剂量显示的是琥珀色「待服用」——同一张卡片上，颜色说"已经错过"，文字说"还来得及"。已把 `isOverdue` 传进胶囊。

**实测**：修复后 22:49 的剂量显示红色「未服药」+「已到时间 · 已过 12 分钟」。

### 5.4 今日卡片的「已过 N 分钟」被拆开且错位

**现象**：今日卡片的提示文字被拆成「已过 149 分」/「分钟」，第二行还相对卡片其他内容明显错位。

**三个叠加的根因**：

1. **时间与提示被塞进同一个普通 `Row`，两边都没有权重**：提示只能拿到 "21:05" 之后的**残余**宽度，于是被挤成两三行；而 `CenterVertically` 又把这个变高的文本与时间做了垂直居中，换行后的行首与卡片其他文字不在同一条左边缘上 —— 看起来就是"错位"。
2. **中文可以在任意两个字之间断行**：所以即使数字与单位之间用不换行空格，单位词本身仍会在「分」「钟」之间被撕开（这一点是实测才发现的：先加了 `U+00A0`，最大字号下依旧断在「分/钟」之间）。
3. **提示重复了状态胶囊已经说过的内容**（"已完成 · "），白占宽度 —— 正是它让这行在最大字号下放不下。

**修复**：

1. 时间移到**药名同一行、右对齐**（时间在加权药名之前测量，永远不会被挤没），状态提示**独占一行**、拿到整张卡片宽度。
2. 数字与单位之间用 `U+00A0`，单位词内部用 `U+2060`（WORD JOINER，UAX #14 的 WJ 类，明确禁止在该位置断行）。整句因此只会**整体**换行，不会从中间被切开。
3. 提示不再复述状态 —— 只回答"距离计划时间多久"（"已过 152 分钟" / "还有 20 分钟"），状态由胶囊用颜色 + 图标 + 文字表达。

**实测**：系统字号 2.0（总倍数封顶 1.6×）下，卡片显示「已过 152 分钟」单行完整、无错位；两张卡的时间列右对齐成一条线。

## 六、仍然存在的边界（如实说明）

- **进程被系统彻底清理**（强制停止 / 厂商一键清理）时收不到解锁广播；此时只能等用户打开应用，打开的那一刻会立刻补提醒。
- **全屏提醒**在 Android 14+ 需要用户在系统设置里手动允许，未允许时退化为横幅 + 震动。
- 「普通重复提醒」（设置里的「重复提醒间隔」）与「解锁补提醒」是**两套独立机制**，各自有各自的次数上限；两者都会响，这是刻意的（一次是到点没处理，一次是用户回来了）。
