# 文案与术语规范（v2.1.0 起）

这份文件是**界面文案的唯一依据**。改文案前先看这里；这里有规定的按这里写，这里没规定的按下面的原则处理。

新增术语请补进对应表格，否则下一个人会重新发明一个说法。

---

## 一、为什么要统一

1.9.0 及以前，同一个概念在不同界面有三四种说法（「服药时间」「用药时间」「计划时间」「该吃药了」），
用户得先猜它们是不是一回事。术语不一致的代价不是不美观，而是**用户无法确认自己操作的是不是同一件事**。

所以规则是：**一个概念只有一个词**，在通知、设置、编辑器、知识库、小组件里完全一致。

### 2.7 应用锁（v2.1.0 起语义变了）

应用**自己不做**应用锁——不做密码、不做指纹、不校验生物识别，因为这个应用里没有值得设一道
独立密码的东西，而多一道锁只会在半夜提醒时挡住用户。

| 用 | 不用 |
| --- | --- |
| 应用锁 | 应用密码、锁屏密码 |
| 打开系统的应用锁设置 | 开启应用锁、设置密码 |

界面上这一项的措辞必须让用户明白：**锁是系统提供的，应用只是把它打开**。

## 三、写法原则

### 3.1 少用口语，直接说结果

| 不写 | 改写 |
| --- | --- |
| 药快没了，记得补货哦～ | 库存不足，请及时补充 |
| 该吃药啦！ | 该服用：阿司匹林 |
| 一不小心就漏了？ | 未服药会记录在历史里 |
| 设置里点点就能改 | 可在设置中修改 |

原因：这个应用的读者包括老年人和视力不佳的人，**口语化的语气词会挤占信息密度**，而他们更需要
在最短的字数里看到「是什么、什么时候、多少」。语气词不提供信息。

但**不要因此写成说明书语**：能用「该服用了」就不要用「应于规定时间执行服药操作」。

### 3.2 一句话只说一件事

> 反例：「提醒不追求精确到秒，而是尽量在你方便的时候、用你容易接受的方式告诉你。」
> —— 三个分句、两个转折，读者读完不知道自己该做什么。

> 正例：「提醒会提前几分钟发出，避免你正在忙别的事。」

### 3.3 说清「会怎样」，而不是「我们做了什么」

| 不写 | 改写 |
| --- | --- |
| 使用 setExactAndAllowWhileIdle 排定 | 会在设定时间准时提醒 |
| 已写入 reminder_events | 已记录这次提醒 |
| 通道重要性 HIGH | 会弹出顶部横幅 |

例外：开发者选项、以及面向排查的自检页面，可以直说技术细节——那里的读者就是要技术细节。

### 3.4 按钮用动词，标题用名词

- 按钮：「开始新一轮」「停止响铃」「立即下载」「去搜索」「我知道了」
- 标题：「复查提醒」「响铃方式」「下载方式」

### 3.5 长度

- 折叠摘要：≤ 28 个字（一行不折行）
- 开关副标题：≤ 40 个字（两行内）
- 通知正文：≤ 60 个字，细节放展开区
- 按钮：≤ 6 个字

### 3.6 数字与单位

- 数字与单位之间加空格：「5 分钟」「3 次」「0.5 ml」
- 时间用 24 小时制：「08:00」，不用「早上 8 点」——**但通知标题例外**，那里保留「早上 8 点左右」
  的人话表达，精确时间放在展开区（这是 1.9.0 的既定设计，见工程说明第 12 节）

## 四、必须保留的表述（不要「优化」掉）

这几句是刻意写的，改动会削弱功能本身：

1. **「本应用只做用药记录与提醒，不提供任何诊断、治疗或用药建议。」** —— 免责的核心，一字不改。
2. **「应用不可能知道你的药吃多久要复查。」** —— 复查提醒的第一句，它解释了为什么需要用户自己填。
3. **「复查提醒中的阈值由你自己填写」** —— 同上。
4. **「只有你按这个按钮时才会打开浏览器」** —— 搜索入口的隐私说明。
5. **「已跳过」与「未服药」是两个不同的状态** —— 依从率统计依赖这个区分，不要合并成「没吃」。
6. **知识库每篇结尾的「不能替代医嘱或药品说明书」** —— 不要为了排版删掉。
