# 药准时 / MediTrack

离线优先的用药提醒与记录应用。自定义药品、多个服药时间、每日服药数量记录，以及一个**优先显示“还没吃”和“马上要吃”**的桌面小组件。

> **免责声明**：本应用只做用药记录与提醒，**不提供任何诊断、治疗或用药建议**。请严格遵照医生或药师的处方服药；任何剂量调整、停药或换药请先咨询专业医疗人员。提醒功能依赖系统闹钟与通知服务，在省电模式、后台限制或权限被收回等情况下可能延迟或失效，请勿把它当作唯一的用药保障手段。

## 1. 需求确认

| 目标 | 实现方式 |
| --- | --- |
| 离线优先、长期可靠 | 无 `INTERNET` 权限；全部数据在 Room + DataStore 本地存储 |
| 自定义药品 | 名称、图标、颜色标签、剂型、单位、规格、每次剂量、单次上限、服用时机、备注、库存 |
| 多时间提醒 | 一个药品可挂任意多个提醒时间，每个时间独立设置重复规则 |
| 重复规则 | 每天 / 隔天 / 每周指定 / 每 N 天 / 吃 X 天停 Y 天 |
| 数量记录 | 加号减号步进，支持液体 0.5 步长；每次操作写入审计日志 |
| 状态自动判定 | 达到计划 → 已服用；低于计划 → 部分服用；为 0 → 未服用 |
| 到点提醒 | AlarmManager 精确闹钟 + 通知，通知带 **已服 / 稍后 10 分钟 / 跳过** |
| 漏服处理 | 超过宽限期自动标记漏服并二次提醒 |
| 重启有效 | BOOT_COMPLETED 接收器重排全部闹钟 |
| 桌面小组件 | Jetpack Glance，单一可缩放条目（默认 4×2，最小 4×1）；按 即将服用(黄) > 未服药(红) > 今日稍后 > 已服用(绿) > 已跳过 排序 |
| 历史与统计 | 月历热力标记、依从率、连续服药天数、漏服次数、按药品筛选 |
| 备份恢复 | JSON 全量备份与恢复、CSV 记录导出 |
| 主题 | Material 3、动态取色、浅色/深色/跟随系统、三套主题色 |
| 适老 | **可选**大字体、高对比度、简化模式、超大触控目标、一键预设 |

**明确不做**：诊断建议、处方推荐、云同步、账号体系、网络请求。

**分层**

```
UI (Compose) -> ViewModel (StateFlow) -> Repository -> Room DAO / DataStore
                                            |
                                   domain/plan 纯函数引擎
```

关键设计决策：

1. **时间用 epoch-day，不用毫秒**。所有“哪一天”的判断都用 `LocalDate.toEpochDay()`，时刻用“距当日零点的分钟数”。夏令时、跨时区、跨月都不会出现差一天的经典 bug。日历网格、重复规则、漏服扫描全部基于它。
2. **重复规则是纯函数**。`RepeatingRule.matches(epochDay, slotStartEpochDay)` 不依赖 Android、不依赖时区，可以在 JVM 上完整单元测试。
3. **DoseLog 快照计划剂量**。今天该吃 1 片被记录在 `dose_logs` 行里。用户之后把药品改成 2 片，昨天历史依然显示 1 片——历史必须如实反映当时的情况。
4. **剂量行按天物化**。`DayPlanner` 把 schedule 展开成“今天的每一次服药”，`DoseRepository.materializeDay()` 落库。提醒通知因此永远有一行可写，即使用户当天从没打开过应用。
5. **状态只由数量推导**。没有任何地方能“直接设置状态”——`DoseRepository.statusFor()` 是唯一定义，加号、减号、通知按钮、小组件按钮、撤销全部走它。
6. **单一通知接收器**。所有闹钟都指向 `ReminderReceiver`，服药闹钟、稍后到期、心跳自检、开机重排共用一条代码路径。
7. **退化为可用而非崩溃**。没有精确闹钟权限时自动降级为 `setAndAllowWhileIdle`；数据库读取失败时小组件显示空态而不是“加载失败”。

**桌面小组件（v1.4.0 简化）**

小组件在桌面的组件列表里**只有一个条目**，默认 4×2，用户拖动边缘即可放大（最小 4×1，即 250×40dp）。
不再有多尺寸选择项——每一档本来就能自由缩放，而布局完全由格子的真实尺寸算出，所以一个可拖动的条目既更简单也更不容易出错。

排序与配色（核心产品承诺）：

| 顺序 | 状态 | 颜色 |
| --- | --- | --- |
| 1 | 30 分钟内即将服用 | **黄色** |
| 2 | 未服药（到点未记录 / 部分服用 / 已判定漏服） | **红色** |
| 3 | 今日稍后 | 中性蓝 |
| 4 | 已服用 | **绿色** |
| 5 | 已跳过 | 灰 |

设计要点：

- **行数由真实高度决定，不由"我是哪个尺寸"决定**。`WidgetSizing.layoutFor()` 是一个纯函数，从 `LocalSize` 推出标题是否显示、能放几行。旧实现用 130dp / 200dp 两个硬阈值查表，落在阈值之上的尺寸就会要求比实际能放下的更多行，超出的部分被 Launcher 裁掉——这就是旧版 2×2 显示错乱的原因。
- **宁可不要标题，不能不要药**。4×1 放不下"标题 + 一行药"，所以丢掉标题。少一个标题远好过把药名裁掉一半。
- **`SizeMode.Exact`**。Glance 默认的 `Single` 模式只在首次创建时组合一次，用户拖动缩放后不会重新组合，缩放过的格子会一直沿用出生时的布局。一个可缩放的单一小组件尤其依赖它。
- **字号跟着系统走**。行高按 `Configuration.fontScale` 缩放——本应用自带"适老模式"会调大系统字号，不跟随的话模型恰好会对最需要看清它的用户裁切内容。
- **状态色改为按主题解析的资源色**。原先用固定 ARGB，用意是"红色在任何主题下都表示漏服"；但同一个颜色不可能在近白和近黑两种卡片上都达到可读对比度（两者要求的亮度区间不相交），固定值必然在其中一个主题下失效——旧的琥珀色状态文字在浅色 Launcher 上几乎看不见。现在保持色相、让明度跟随主题。
- **没有加减按钮**。桌面上一键改动服药数量没有确认、无法撤销、也弹不出"多服"确认框，比打开应用更差；去掉它还给药品名让出了宽度。整行是一个跳转到该次服药的点击目标。
- **刷新间隔 10 秒 ～ 10 分钟，5 档**（10 秒 / 30 秒 / 1 分钟 / 5 分钟 / 10 分钟）。WorkManager 周期任务下限是 15 分钟、`updatePeriodMillis` 下限是 30 分钟，都表达不了这个范围，因此**由后台守护服务驱动**；守护关闭时回落到 15 分钟的 WorkManager 任务，设置页会明确提示。
- **短间隔不等于频繁重绘**：每次先比对负载指纹，内容没变就不重绘。10 秒档的代价因此只是一次很小的数据库读取，换来的是"变化后很快反映到桌面"。
- **预览图由脚本生成**（`tools/make_widget_previews.py`），几何参数与 `WidgetSizing` 同源、颜色与 `colors_widget.xml` 同源，避免手绘预览与实际渲染脱节。
- 「最多显示条目数」这个设置此前**从未被读取过**（只存储和备份），现在它作为行数上限真正生效：能放几行由格子高度决定，显示几行取两者的较小值。

**可靠性设计（重点，v1.1 重写）**

> 本节描述的是**重写后**的提醒架构。参考项目：[vicolo-dev/chrono](https://github.com/vicolo-dev/chrono)。

核心原则一句话：**数据库是唯一事实来源，闹钟只是提示；每一次触发都从零重算并重排全部提醒，且该过程幂等。**

旧实现的做法正好相反——为每个剂量挂一个闹钟，再加一个"次日午夜"的维护闹钟，然后就**信任**它们。任何一个 `PendingIntent` 被 OEM 后台清理、被强制停止、或在 24 小时 Doze 中被丢弃，这个剂量就再也不会响，唯一能修复它的只有用户恰好打开应用。这就是"系统通知调用总是有问题、无法准时通知"的根因。

**四条互相独立的触发路径，全部汇入同一个 `ReminderEngine.reconcile()`**

| 路径 | 触发时机 | 作用 |
| --- | --- | --- |
| 精确闹钟 | 每个剂量的到点时刻 / 提前预告时刻 | 主路径 |
| **自检心跳** | 默认**每 15 分钟** | 丢失任一闹钟，最多延误一个周期 |
| WorkManager 周期任务 | 默认每 15 分钟 | 与闹钟**机制不同**，故障模式不同，互为备份 |
| 系统事件 | 开机 / 时区变更 / 时间变更 / 应用更新 / 启动 / 回到前台 | 立即重建全部排程 |
| **后台守护服务** | 常驻（默认开启） | **唯一能对抗"被系统清后台"的机制**，见下 |

因为 `reconcile()` 幂等，五条路径同时到达也不会重复提醒：先到的做事，后到的发现无事可做。

**关于"只有打开应用才提醒"（v1.3.0 重点）**

前四条路径都是**计划好的唤醒**。而强制停止或厂商 ROM 的"一键清理"取消的正是所有计划好的唤醒——闹钟、Job、心跳全部一起消失，应用在用户再次打开它之前收不到任何广播。症状非常典型：**一个通知都没有，打开应用后一次性全部出现**。加再多的闹钟也没用，它们在同一次清理里一起消失。

所以新增了**后台守护服务**（前台服务 + 一条静音常驻通知），让进程留在前台服务的保护范围内，不被当作可回收的后台进程。同时：

- **闹钟级提醒**改为默认开启（`setAlarmClock` 是唯一不受 Doze 影响的闹钟类型，且系统把它当作用户可见的闹钟对待）；
- 每次排定闹钟时记录"为哪个剂量、排在什么时刻"，之后若发现"排过、时间已过、从未提醒"，明确记为一次 **`ALARM_LOST`**——这把"应用没排"和"系统没触发"彻底分开，用户可以在设置页自己看到证据；
- 设置页提供一键跳转厂商「自启动 / 后台运行」页面（小米 / 华为 / OPPO / vivo / 三星 / 魅族已知组件名逐个尝试，都没有时回落到应用详情页）。

**纠错能力**（每一条都对应旧实现中一种"提醒静默消失"的方式）

- **永不提前**：触发时刻比计划早出容差窗口（默认 5 分钟 + 提前预告窗口）时，判定为时钟跳变或过期 `PendingIntent`，**重新排定而不是弹出提醒**。且该规则只对"声称自己是这个剂量的闹钟"的触发生效——心跳、开机、启动本来就会扫到几小时后的剂量，把它们当异常只会淹没真正的信号。
- **永不迟到太久**：超过 `迟到阈值`（默认 3 小时）的提醒**不再弹出横幅**，降级为静默的「如果已经吃过，点一下补记」提示，避免重启后为早上 8 点的药在凌晨 3 点把人吵醒。
- **提醒次数上限是存储的计数器**，不是从时间推算。旧实现用 `(now - 上次提醒时间) / 重复间隔` 推算次数并截断到上限，结果**时间本身就会耗尽配额**：剂量被提醒过一次后，只要过了 20 分钟，计数就"达到上限"，后续所有重复提醒被静默吞掉。现在 `dose_logs.escalationCount` 是显式自增的计数，`markNotified` 每次 +1。
- **未服药提醒曾经永远发不出来**：漏服扫描与"已通知"标记原本写在同一条 UPDATE 里，而扫描在启动、每次心跳、每次开机都会跑，因此总是抢先占掉标记。现在"推导状态"（`deriveMissed`）与"认领通知"（`markMissedNotified`）是两条独立语句。
- **稍后提醒会重新打开提醒配额**：`snooze` 清空 `notifiedTimeMillis` / `escalationCount` / `preRemindedAtMillis`。"稍后"的语义是"到新时间再好好提醒我一次"，而不是"继续显示我已经放弃的第三次重复"。
- **已稍后（snooze）的剂量不会掉出排程窗口**：排程查询用 `MAX(COALESCE(snoozedUntilMillis, plannedTimeMillis), plannedTimeMillis)`（即"有效到点时刻"）。旧查询只看 `plannedTimeMillis`，用户一按"稍后"，该剂量立刻掉出窗口，只剩 snooze 那一刻挂上的孤零零一个闹钟。
- **精确取消**：已排程的剂量 id 记录在 `ReminderAlarmRegistry` 里，因此"取消全部"是精确操作，而不是对 request-code 区间做猜测，不会留下会响的孤儿闹钟。
- **心跳永不被取消**：例行重算只取消"每剂量"闹钟。若在重算开始时连心跳一起取消、结束时再挂回，中间就存在一个"进程被杀 ⇒ 一个闹钟都不剩"的窗口。
- **决策审计**：`reminder_events` 表记录每一次决策——是哪个触发器、投递还是跳过、跳过原因、以及**系统实际延迟了多少毫秒**。设置页可直接查看，回答"为什么 8 点没有提醒我"。
- **自检与修复**：设置页会核对权限、心跳是否停滞、实测最大延迟，给出可执行建议（含"闹钟级提醒"），并提供「立即自检并修复」与「发送测试通知」。

**人性化提醒方式（不追求精确到秒）**

- **提前预告**：服药前（默认 15 分钟）先提醒一次「还有 15 分钟：阿司匹林」，让人有时间准备；它同时是同一剂量的**第二条独立投递路径**。
- **按人能听懂的方式说时间**：标题是「早上 8 点左右」而不是 `08:00`；精确到分钟的原始时间仍在展开详情里，临床精度不丢失。取整**向下**到 5 分钟：永远不会报出一个比实际计划更晚的时间，也不会跨到相邻时段（08:58 说"早上 8 点 55 分左右"，而不是"上午 9 点"）。
- **合并同一时段**：几分钟内到期的多种药合并成一条摘要通知，子通知保留各自的「已服 / 稍后 / 跳过」按钮。提前预告与到点提醒分别汇总，不会把"还有 15 分钟"和"现在该吃"混在一条里。
- **接受窗口而不是精确时刻**：管线里没有任何一处对两个时刻做相等比较或推理亚分钟精度；闹钟晚到几秒或几分钟都只是"准时"。
- **"稍后"不再凭空消失**：推迟后保留一条安静的「已推迟：阿司匹林 / 将在 08:35 再提醒你」并带「现在服用」按钮，到点被真正的提醒替换。
- **免打扰时段顺延而不是静默**：免打扰时段内到点的提醒会等到时段结束再发，而不是在 23:40 静默发一条没人看得到的通知。
- **晚到就承认晚到**：超过 2 分钟才送达的提醒会在详情里说明"本次提醒比计划时间晚了 N 分钟"。

**其它**

- 精确闹钟：`setExactAndAllowWhileIdle`；无权限时降级为 `setAndAllowWhileIdle`，且心跳兜底，最坏情况是"有界延迟"而不是"静默失效"。
- **闹钟级提醒**（可选，默认关闭）：`setAlarmClock` 完全不受 Doze 影响。代价是状态栏出现闹钟图标，因此交由用户选择；自检会在**实测到**系统延迟后才推荐开启。
- 每日深度自检（03:30，而不是午夜——午夜正是 Doze 最深、OEM 清理任务最活跃的时刻）负责修复历史、物化多日、清理审计表。它已不再是唯一的重建路径。
- 通知重复提醒有次数上限（默认 2 次，含首次），避免无限轰炸。
- v2 → v3 数据库迁移为纯增量（`escalationCount`、`preRemindedAtMillis`、`reminder_events`），由 `tools/verify_migration.py` 在真实 SQLite 上逐列比对 Room 导出的 schema 验证。

## 4. 数据模型

```
medications --1:N--> schedules --1:N--> dose_logs --1:N--> dose_events
     |                    |                 |
  药品定义          提醒时间+重复规则    某天某次的记录      追加式审计日志
```

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `medications` | name, icon, colorTag, dosageForm, unit, strength, doseAmount, maxDoseAmount, foodTiming, note, stockAmount, stockAlertThreshold, reminderEnabled, isActive | `plannedQuantity` 对可数剂型向上取整 |
| `schedules` | medicationId, minuteOfDay, repeatRule, startEpochDay, endEpochDay, reminderEnabled | `repeatRule` 编码为 `TYPE|interval|daysOfWeek|on|off|anchor`，可直接用 SQLite 工具查看 |
| `dose_logs` | medicationId, scheduleId, epochDay, plannedMinuteOfDay, plannedTimeMillis, plannedQuantity, plannedUnit, takenQuantity, takenTimeMillis, snoozeCount, snoozedUntilMillis, missedNotified, overDoseConfirmed, status | 唯一索引 `(scheduleId, epochDay)` 保证幂等 |
| `dose_events` | doseLogId, type, delta, resultingQuantity, resultingStatus, timestamp | 撤销与审计的依据 |

枚举（`MedicationIcon`、`MedicationColorTag`、`DosageForm`、`DosageUnit`、`FoodTiming`、`RepeatRuleType`、`DoseStatus`、`DoseEventType`）一律**按名称**存储，重排常量不会污染既有数据；未知名称回落到安全默认值。

`DoseStatus` 生命周期：

```
UPCOMING --(时间到)--> DUE --(加号)--> PARTIAL --(达到计划)--> TAKEN
                        |                 |
                        +--> SKIPPED      +--(减到 0)--> DUE
                        |
                        +--(超过宽限期)--> MISSED
```

## 5. 页面原型说明

**底部 4 个 Tab**

1. **今日** — 顶部大号 `3/5` 进度 + 进度条 + “下一次：18:00 阿司匹林”；下方按时间排序的药品卡片（颜色导轨、图标、名称、时间、相对提示、规格/时机/备注、数量步进器、状态胶囊、“标记已服”）。顶部有 前一天/今天/后一天 切换。卡片菜单含：编辑、跳过、稍后提醒、撤销上一步、重置记录。全部完成时显示“今日用药已完成 ✅”。
2. **药品** — 搜索框 + 全部/启用中/已停用 筛选；每行显示图标、名称、时间串、规格与重复规则标签、库存（不足时红色 + 警告图标）、启用开关、删除按钮。
3. **历史** — 月历（每格一个语义色点）+ 常驻图例；统计卡（依从率大号数字、连续/最长服药天数、总计划/已服/部分/漏服/跳过次数、累计数量）；范围切换 7/30/90 天；下方是选中日期的明细，漏服/跳过可“补记”，已服可“撤销”。
4. **设置** — 权限 → 提醒 → 外观 → 适老与无障碍 → 桌面小组件 → 数据 → 其他（应用锁、关于）。

**其他页面**：添加/编辑药品（四个分区卡片 + 时钟表盘选择时间 + 日历选择起止日期）、权限引导页、关于与免责声明页。

**图标风格**：Material Symbols Rounded 语义（线性圆润）。规则是**未服用用 outlined、已服用用 filled**，仅凭形状就能读出列表状态。

**应用图标**：自适应图标，前景为“药片 + 时钟”组合（108dp 画布，内容收在中央 72dp 安全区），背景为薄荷绿 → 青蓝线性渐变，并提供 **monochrome** 变体以支持 Material You 主题图标。

**背景**：浅色 `#FBF7F2` 暖米白；深色 `#121212`。

**圆角与留白**：卡片 20dp（简化模式 24dp）、胶囊全圆角、底部弹层 28dp；屏幕内边距 16dp，卡片间距 10–12dp。

### 已实现的自动化单元测试（`app/src/test`，纯 JVM，无需设备）

**RepeatRuleTest** — 重复规则引擎
- 每天：起始日当天生效、之后每天生效、起始日之前一律不生效

**DayPlannerTest** — 状态推导与漏服升级
- 未来 → 未到时间；已过且为 0 → 待服用；0 < x < 计划 → 部分服用；达到/超过 → 已服用

### 10.2 在设备上复现并修复的 4 个真实缺陷

拿到模拟器后逐项复现用户反馈，确认并修复了以下问题。**这些问题之前的"编译通过 + 单元测试通过"完全无法发现**——这也是为什么必须做真机级验证。

**① 「添加药品」按钮点击即崩溃（P0，用户报告）**

崩溃栈明确指出原因：

```
java.lang.IllegalArgumentException: Navigation destination that matches request
NavDeepLinkRequest{ uri=android-app://androidx.navigation/medication_editor?arg=0 }
cannot be found in the navigation graph
    at androidx.navigation.NavController.navigate(NavController.kt:1819)
    at com.meditrack.MediTrackRootKt$MediTrackNavHost$2$5$2$1.invoke(MediTrackRoot.kt:241)
```

根因：目标路由**声明**为 `medication_editor?arg={medicationId}`，而代码**导航**到 `medication_editor?arg=0`。Navigation 是把"填好值的具体路由"与"声明的模式"做匹配，字面量 `0` 永远匹配不上占位符 `{medicationId}`，于是抛异常。修复：统一占位符名称为 `arg`（即 `medication_editor?arg={arg}`），并把 ViewModel 读取的 SavedStateHandle key 与路由声明绑定为同一常量，避免再次漂移。

**② 「历史」页点击后整页空白（P0，用户报告）**

在模拟器上稳定复现：进入「历史」后进程存活但界面全白，日志中抛出
`java.lang.ArrayIndexOutOfBoundsException: length=0; index=-5`（`SlotTableKt.key` ← `ComposerImpl.endRoot`），即 Compose 的 slot table 被破坏。

通过**二分定位**（临时开关逐段禁用页面区块）锁定触发组合：日历网格 + 每日单元格里使用 `StatusDot`（其内部调用 `clearAndSetSemantics{}`），在约 42 个单元格的首次合成中破坏了组合结构。修复：

- 单元格里的圆点改为普通 `Box`，不再逐格清除语义
- 单元格高度由 `Modifier.aspectRatio` 改为固定高度（`aspectRatio` 作用在 `weight(1f)` 子项上，会让父 Row 依赖尚未解析的主轴尺寸，测量存在歧义）
- 页面由 `LazyColumn` 改为 `Column + verticalScroll`（页面只有 3 个区块，惰性虚拟化没有收益，却引入了 SubcomposeLayout 子合成）

**③ 「添加药品」按钮重复出现（用户报告）**

「今日」与「药品」两个页面的 Scaffold 各自渲染了一个 FAB，而空状态区块里**又**渲染了一个 `ExtendedFloatingActionButton`，于是空列表时同时显示两个一模一样的按钮。已删除空状态里的那个，只保留 Scaffold 的唯一 FAB，空状态改为文案引导「点击右下角的「添加药品」开始」。

**④ 两个会直接影响用药记录的逻辑缺陷（单元测试发现）**

1. **服药时间前记录部分剂量被误判为"未到时间"**。原 `deriveStatus` 先判断时钟再判断数量，用户 07:30 为 08:00 的药记录半片时显示"未到时间"。已改为先看已记录数量、再看时钟：吃满即"已服用"（提前吃也是吃），有量未满即"部分服用"，再判断稍后提醒，最后才用时钟区分"未到时间 / 待服用"。
2. **小组件排序使用了分钟数而非绝对时刻**。原排序键 `plannedMinuteOfDay` 在夏令时切换或提醒跨午夜时可能与真实触发时刻不一致。已改为按 `plannedTimeMillis` 排序（分钟数仅用于显示）。

另修正一处 lint 判定的配置错误：`backup_rules.xml` / `data_extraction_rules.xml` 中对**未被 include** 的 `files/exports/` 写了 exclude，已改为"干脆不 include"，既消除报错又保持导出文件不进云备份的语义。

### 10.3 防回归测试

为 ① 与 ② 各补了会失败的测试，确保同类问题不会再次溜过去：

- `RoutePatternTest`（6 个单元测试）：断言"声明的路由模式"与"实际导航的目标"使用同一个参数名，并断言 ViewModel 读取的 key 与路由声明一致。原缺陷会被这条断言直接拦下。
- `NavigationSmokeTest`（5 个仪器化测试）：在真实 Activity 上点击按钮、切换 Tab，断言目标页面确实渲染出来。路由图只在运行时存在，这类问题只能这样测。
- 为此引入了 `MediTrackTestTags`：测试按稳定 tag 定位控件，不依赖会变的中文文案（且 Button 内的 Text 会被合并进按钮语义节点，按文本查找本身也不可靠）。

### 单元测试暴露并修复的两个真实缺陷

测试不是走过场——它抓到了两个会直接影响用药记录的 bug：

1. **服药时间前记录部分剂量被误判为“未到时间”**。原 `deriveStatus` 先判断时钟再判断数量，用户 07:30 为 08:00 的药记录半片时，界面显示“未到时间”而不是“部分服用”。已改为**先看已记录数量、再看时钟**：吃满即“已服用”（提前吃也是吃），有量未满即“部分服用”，再判断稍后提醒，最后才用时钟区分“未到时间 / 待服用”。
2. **小组件排序使用了分钟数而非绝对时刻**。原排序键为 `plannedMinuteOfDay`，在夏令时切换或提醒跨越午夜时可能与真实触发时刻不一致，导致“马上要吃”的药排到后面。已改为按 `plannedTimeMillis` 排序（分钟数仅用于显示），并修正了测试辅助函数，保证两者在测试中一致。

另外修正了一处 lint 判定的配置错误：`backup_rules.xml` / `data_extraction_rules.xml` 中对**未被 include** 的 `files/exports/` 写了 exclude 规则（对未包含的域写排除是无意义规则），已改为“干脆不 include”，既消除报错又保持导出文件不进云备份的语义。

### 10.4 仍未验证的部分（如实说明）

已在 Android 14 模拟器上完成导航、渲染与崩溃回归验证。以下仍**未经运行时验证**，因为它们依赖真实系统行为而非应用逻辑：

- **通知的实际投递**：精确闹钟按时触发、通知按钮回调、免打扰时段、重启后重排——需要在真机上设定一个 1 分钟后的提醒并锁屏验证。
- **桌面小组件的实际渲染**：Glance 在真实 Launcher 上的单一可缩放小组件（拖动到 4×1、4×2、4×3… 后的重排）、状态配色、10 秒～10 分钟刷新节奏——需要在真机长按桌面添加小组件验证。
- **厂商 ROM 差异**：国产 ROM（OriginOS / MIUI / ColorOS 等）对后台、自启动、精确闹钟的限制策略比 AOSP 严格得多。已修复的问题是平台无关的代码缺陷，但仍建议在真机上走查一遍第 9 节清单，并确认「设置 → 权限」三项均为已授权。
- 模拟器输入坐标与显示坐标存在缩放差异（本次调试中已确认并绕过），这只影响 adb 脚本点击，与应用无关。

> 结论：**"能编译、能过单元测试"不等于"能用"**。本次 4 个缺陷中有 3 个（崩溃、空白页、重复按钮）都是只有在设备上点一下才会暴露的，建议后续改动同样先跑 `connectedDebugAndroidTest`。

## 12. 本次新增：提醒与设置的定制化

这一轮针对「提醒不够灵活、时间选择不好用、缺少按日期服药、缺少未服药红标、以及希望手机闲置时先别提醒」做了以下改动。

### 12.1 提醒方式可以分别自定义

设置 → 提醒：

| 选项 | 说明 |
| --- | --- |
| 提醒铃声 | 到点是否响铃 |
| 震动 | 到点是否震动 |
| 顶栏横幅弹出 | 是否在屏幕顶部弹横幅并显示在锁屏上；关闭则只在下拉通知栏里显示 |
| 静音时仍然响铃 | 按闹钟处理，静音也出声（默认关闭） |

**实现要点**：Android 在通知渠道创建后就**冻结其重要性等级**，而「顶栏弹出」正是由重要性决定的。所以应用维护两个提醒渠道并按设置路由 —— `meditrack_reminder_alert`（IMPORTANCE_HIGH，弹横幅、上锁屏）与 `meditrack_reminder_quiet`（IMPORTANCE_DEFAULT，只在通知栏）。铃声与震动则在每条通知上显式设为 null 或具体值，否则会回落到渠道默认值、让用户的开关失效。两个渠道同属一个渠道组，在系统通知设置里显示在一起。

### 12.2 时间选择改成上下拖动式

原来的时间选择用的是 Material 3 的**圆盘**（`TimePicker`）。圆盘对本应用的目标用户并不合适：小时刻度只有几毫米、分钟刻度约 8dp 间距，设一个 08:00 需要两次精准的圆周拖动。

现在改成**上下拖动的滚轮**（[WheelPicker.kt](app/src/main/java/com/meditrack/ui/components/WheelPicker.kt)）：

- 小时、分钟各一列，惯性滚动 + **自动吸附**到整格，不会停在两格之间
- 首尾都用 `contentPadding` 补齐半个高亮带，所以 0 点和 59 分都能滚到正中
- 选中值**由滚动位置派生**，拖动与回调不可能不一致
- 离中心越远透明度越低，读起来像滚轮而不是列表
- 整个滚轮是一个无障碍节点（「当前选中：08」），而不是 24 个可滚动文本
- 24 小时制时只有两列；12 小时制自动多出「上午/下午」一列

### 12.3 按「每月几号」服药 + 日历选日期

重复规则新增 **每月几号**（`RepeatRuleType.MONTHLY_DATES`）：可多选 1–31 号，也可点「从日历选择日期」直接用日历挑一天。

**短月份的处理**（这是关键设计决定）：选了 31 号而 2 月没有 31 号时，会在**该月最后一天**提醒，而不是静默跳过。对用药提醒来说，悄悄漏掉一次是最糟的结果。所以「31 号」在短月份读作「最后一天」。界面上也把这条规则写给了用户：「例如选了 31 号，2 月没有 31 号时会在 2 月最后一天提醒。」

编辑器里原有的开始/结束日期仍然使用系统日历选择器。

### 12.4 过了时间没吃 → 红色「未服药」

新增 `DoseView.isOverdue`：**计划时间已过且没有任何记录**即为逾期，状态胶囊立刻变红并显示「未服药」。

它刻意**领先于**存储状态：如果只等超时扫描把状态改成 MISSED，那么一个已经迟到 20 分钟的剂量在界面上仍是橙色的「待服用」，读起来像「还来得及」，而事实是时间已经过了。已经吃了、部分服用、已跳过都不算逾期 —— 用户已经做过操作，胶囊本身已经说明了状态。

全应用统一了措辞：今日卡片、小组件、历史图例与统计、通知标题都使用「未服药」。

### 12.5 手机长时间没用 → 先不提醒，开始用立刻补提醒

**这一个功能默认关闭**（你特别要求的），设置项在「设置 → 提醒 → 手机未使用时暂缓提醒」。

| 行为 | 说明 |
| --- | --- |
| 默认状态 | **关闭**。关闭时应用不读取任何手机使用状态，也不注册任何监听 |
| 开启后 | 手机闲置超过设定时间、或息屏时，到点的提醒**先不发**，而是在剂量行上标记「待补发」 |
| 用户回来后 | 解锁或亮屏的那一刻，立刻补发通知；多项会合并成一条「N 项用药提醒」，逐条也在通知栏里 |
| 超过未服药判定时间 | 不再当作新提醒播报，按「未服药」记录（今日页红标、历史可见） |
| 可配置 | 启用开关、多久算「没人用」（10–120 分钟）、息屏时是否也暂缓 |

**为什么不需要「使用情况访问」权限**：读取 `PACKAGE_USAGE_STATS` 会让应用能看到你打开过的**所有**应用 —— 对「睡着了别吵我」这个需求来说是完全不相称的权限。这里只监听普通的活动广播：`ACTION_USER_PRESENT`（解锁）、`ACTION_SCREEN_ON`/`ACTION_SCREEN_OFF`。

这些广播**不能在清单里静态注册**（平台禁止，属于滥用向量），只能在运行时注册 —— 这正好也保证了「关闭时真正不监听」：开关关闭时不注册任何接收器，而不是注册了再忽略。设置里改动开关会**立即生效**，不需要重启应用。

「待补发」标记写在数据库行上（`dose_logs.deferredAtMillis`），所以这个承诺能挺过进程被杀和手机重启；启动、开机维护、打开应用时都会尝试补发一次。

### 12.6 数据库升级到 v2（保留了真实数据）

新增两处字段：

- `dose_logs.deferredAtMillis` —— 补发标记，默认 null 正好等同 v1 行为，无需回填
- `schedules.repeatRule` —— 编码格式追加了 `daysOfMonth` 字段；**v1 的六段字符串仍然可读**，缺失字段按空处理

写了真正的 `ALTER TABLE` 迁移而不是 destructive fallback：用户可能已经记录了几个月的数据，不能因为一次版本升级就抹掉。并且用 `MigrationTestHelper` 实测：建 v1 库 → 插入药品/计划/服药记录 → 跑迁移 → 读回校验数据仍在、新列可用。

## 13. 复现本次验证（模拟器环境）

设备级验证使用自建 AVD（放在非系统盘，避免占用 C 盘空间）：

| 项 | 位置 |
| --- | --- |
| Android SDK（emulator / platform-tools / platform-34 / system-image） | `$ANDROID_SDK_ROOT` |
| AVD 配置 | `$ANDROID_AVD_HOME\meditrack34.avd` |
| 系统镜像 | `system-images;android-34;google_apis;x86_64` |
| 已验证系统 | Android 14（API 34），1080x2340 @ 320dpi，WHPX 加速 |

启动模拟器：

```powershell
# 按自己的安装位置设置这三个变量即可
$env:ANDROID_SDK_ROOT  = "X:\Android\Sdk"
$env:ANDROID_AVD_HOME  = "X:\Android\avd"
$env:ANDROID_EMULATOR_HOME = "X:\Android\userhome"
& "$env:ANDROID_SDK_ROOT\emulator\emulator.exe" -avd meditrack34 -gpu swiftshader_indirect
```

跑测试与打包：

```powershell
gradle :app:testDebugUnitTest            # JVM 单元测试
gradle :app:connectedDebugAndroidTest    # 设备级测试（需模拟器/真机在线）
gradle :app:assembleDebug :app:assembleRelease
```

**注意（仅影响 adb 脚本，不影响应用）**：该 AVD 的输入坐标与显示坐标存在缩放差异——`adb shell input tap` 的坐标空间约为 872x1890，而显示为 1080x2340。用脚本点击时需要按约 1.2385 缩放；更稳妥的做法是直接用仪器化测试按语义定位控件（本次即采用后者，不受坐标影响）。
